## 问题清单
### P2-1 「Verify shadow mode」用存在性检查恒失败——runs/ledger.jsonl 是 tracked 文件，checkout 后必存在
- 描述：`if [ -f "runs/ledger.jsonl" ]; then ... exit 1; fi` —— 本 commit 树内 `runs/ledger.jsonl` 是被追踪的审计账本（`git ls-tree` 确认 blob 存在），checkout 后文件必然存在，该步骤对每次 workflow_dispatch（含非月末 no-op 路径）都会 exit 1。shadow 模式的 CI 信号因此恒红，无法区分「真的没写账本」与「检查本身坏了」；且若真发生越权写入，红色噪声环境会淹没告警。
- 位置：`.github/workflows/e3-forward.yml:55-61`
- 影响范围：E3 forward workflow 所有手动运行（shadow 验证失效）。
- 修复建议：run 前记录 `md5sum runs/ledger.jsonl`，run 后比对不一致才 exit 1（或 `git diff --exit-code -- runs/ledger.jsonl`）。
- 修复成本：低
- 状态：未修复（main 上该步骤原样存在）

### P2-2 scheduler 固定传 `provider_cutoff=None`，被 runner 兜底为 predict_ts——把 AUD-06 要拦的伪造值接进了 live 路径
- 描述：`provider_cutoff = None  # ...use predict_ts from forward_commit_runner. This is the conservative default` —— 7e666d8 的 runner 对 None 值执行 `actual_provider_cutoff = predict_ts`，且 readiness 门无伪造检测（见 7e666d8 报告 P1-1/P2-1）。即：一旦 owner 批准契约并去掉 shadow，每月月末的正式 commit 都会以「模型知识截止=预测时点」这一未经核实的断言进入 ledger。把 predict_ts 称为 "conservative default" 与 AUD-06 的立场相反。
- 位置：`scripts/e3_forward_trigger.py:217-219`
- 影响范围：E3 live headline commits 的来源可信度（cutoff-controlled 因果论证的 provenance 记录）。
- 修复建议：在 YAML 契约中显式配置 `provider_cutoff`（owner 核实 GLM 真实 cutoff 后冻结），trigger 读取之；缺省时 fail-closed 而非回落 predict_ts。
- 修复成本：低
- 状态：未修复（main 上 trigger 仍传 None、runner 兜底仍在）
