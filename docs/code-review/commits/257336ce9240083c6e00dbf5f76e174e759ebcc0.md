## 对照参考
- pandas 官方 to_parquet/read_parquet + Arrow pandas metadata：round-trip 依赖 Arrow schema metadata 保持 dtype，建议固定 pyarrow 引擎并在读回后校验 dtype（pandas.pydata.org、arrow.apache.org/docs/python/pandas.html）——本 commit 的面板全是 float64/str/datetime（无 categorical/nullable-int 脆弱类型），且测试用 `pd.testing.assert_frame_equal` 锁定 round-trip，符合官方建议。
- Parquet schema evolution：对"新增可选列"的惯用做法是读端存在性检测或 `pyarrow.unify_schemas`（Arrow docs / stackoverflow.com）——本实现选择按文件存在性返回 None，对单 run 目录场景是更简单的正确解。

## 问题清单
### P3-1 meta.json 的 `schema` 字段无条件写 2，失去判别力
- 描述：`"schema": 1,` → `"schema": 2,` 的修改在 `save_run` 中是无条件的——即使调用方不传任何 oos/ls 面板（schema-1 式保存），meta.json 也标 `schema: 2`。docstring 却说 "Omitting them leaves the run dir unchanged (schema-1 callers)"——目录内容除 meta 外未变，但 schema 标签已失真；下游若按 `meta["schema"] >= 2` 判断产物存在会误判（实际 load_run 用文件存在性，故当前无害）。
- 位置：`src/aionis/reporting/results.py:177`（main 版本仍在）
- 影响范围：meta 字段的消费方（目前仅 dashboard 用存在性判断，无实际故障）。
- 修复建议：`"schema": 2 if (oos_state is not None or oos_base is not None or ls_returns is not None) else 1`，或改用 `"artifacts": [...]` 列表字段。
- 修复成本：低
- 状态：未修复

### P3-2 L-S 收益落在全局固定文件而非设计文档的 per-run 路径
- 描述：设计文档（ecd68a1b §5.1 Gap 2）规划 `runs/results/<sig>/ls_returns.parquet` + `results.load_ls_returns()` 读取器；实现改为全局 `runs/strategy_returns.parquet`（`scripts/strategy_eval_run.py:52`，每次运行覆盖、无读取器封装）。策略回报跨 phase 无单一 sig，全局文件有其合理性，但 (a) 覆盖即失历史（仅账本存标量），(b) 相对路径依赖 CWD（dashboard 侧用 `results_dir().parent / ...` 锚定读取，脚本侧写入仍是相对路径——从非仓库根运行会写错位置，与 commit 5f227b33 的 P3-2 同族）。
- 位置：`scripts/strategy_eval_run.py:52,135-136`
- 影响范围：dashboard equity 曲线的数据来源可靠性。
- 修复建议：脚本侧用 `results_dir()` 锚定同一路径，消解读写两侧路径基准不一致。
- 修复成本：低
- 状态：未修复
