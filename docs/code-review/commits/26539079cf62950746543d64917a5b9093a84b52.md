## 对照参考
- TP 判定要求 (sic_sector, direction, mechanism_keyword, horizon_bucket) 四元组完全相等，与 seqeval/SeqScore 的 span 级"边界+类型全对才算 TP"的确定性评估哲学一致（github.com、arxiv.org）；无效预测按空处理并单列 invalid_schema，是 CoNLL 评测脚本对 malformed 输出的常见容错方式。
- `compute_input_sha256` 用 sorted-keys 紧凑 JSON + 浮点 round(…,10) 归一化求哈希，与 JSON Canonicalization Scheme (JCS, tools.ietf.org) 的思路一致；原子写 tempfile+os.replace 是 Python 官方文档推荐模式。

## 问题清单
### P3-1 write_report 的 fail-closed 存在 check-then-act 竞态，且 default=str 可能掩盖序列化问题
- 描述：`if output.exists() and not overwrite: raise FileExistsError` 与随后的 `os.replace(tmp_path, output)` 之间无锁；并发写同一目标时后者会静默覆盖先到者，违背"record-once"意图。另外 `json.dumps(..., default=str)` 会把意外类型静默转为字符串而非报错，可能产生未被察觉的非规范字节。
- 位置：`src/aionis/extraction/eval_report.py:200-236`
- 影响范围：离线单用户场景下几乎无影响；仅多进程/重入场景有覆盖风险
- 修复建议：Windows 上可用 `os.open(output, O_CREAT|O_EXCL)` 创建最终文件后写入；或接受现状并在 docstring 标注"非并发安全"。default=str 可收紧为显式白名单。
- 修复成本：中
- 状态：未修复（后续无针对该文件的改动）

### P3-2 gold_sampler 死代码守卫与重复 rejection 记录
- 描述：`rec.filed_ts.year if rec.filed_ts else 0` 中 `else 0` 分支不可达（Step 1 已拒绝 missing_filed_ts）；同一 event_id 出现 ≥3 个不同 hash、或同一冲突对重复出现时，`rejected` 会追加多份 `event_id_hash_conflict` 记录，统计口径略脏。
- 位置：`src/aionis/extraction/gold_sampler.py:167`、`src/aionis/extraction/gold_sampler.py:106-121`
- 影响范围：仅审计输出可读性，采样结果不受影响
- 修复建议：删除死守卫；冲突检测先聚合再每冲突输出一条。
- 修复成本：低
- 状态：未修复

### P3-3 金标外预测事件不进入统计（已知限制，建议文档化）
- 描述：`evaluate_extraction` 只遍历 `gold_records`，`predictions` 中 event_id 不在金标样本里的条目被静默丢弃——即样本外 FP 不可见。这是金标采样评估的标准做法（frozen spec 也如此规定），但值得在 docstring 明示为"样本内 FP"。
- 位置：`src/aionis/extraction/eval_metrics.py:396-409`
- 影响范围：指标解释口径
- 修复建议：docstring 加一句"predictions outside the adjudicated gold sample are not penalized"。
- 修复成本：低
- 状态：未修复
