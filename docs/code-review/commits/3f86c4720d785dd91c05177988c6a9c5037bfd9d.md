## 对照参考
逐项检查点式续跑与社区标准做法一致（[requests-cache](https://requests-cache.readthedocs.io/) 的 SQLite 持久缓存按 URL 键续跑、[Stack Overflow 经典模式](https://stackoverflow.com/questions/16063258/web-scraping-and-python-and-sqlite-how-to-store-scraped-data-effectively) 的 INSERT-OR-IGNORE 检查点、[Scrapy JOBDIR](https://scrapeops.io/python-web-scraping-playbook/scrapy-save-data-sqlite/)）；差别在于成熟方案的缓存键包含全部输入维度（URL+参数），本实现的键只有 ticker——正是内部评审 HIGH 指出的缺口。出处域名：requests-cache.readthedocs.io、stackoverflow.com、scrapeops.io。

## 问题清单
### P1-1 每-ticker 缓存键不含 (start, end) 窗口，改窗后静默复用旧窗事件表
- 描述：`fp = PDIR / f"{t}.json"`，缓存内容 `{ticker, cik, sic, events}` 无窗口信息。若日后把 `START, END` 常量调整（如 END 顺延一年再跑），已缓存的 ticker 直接复用旧窗事件列表——窗外（新增月份）的 13D 申报被静默丢弃，错误数据无声进入 confirmatory 管线。评审原文："changing START/END between runs would silently reuse the old-window event list — dropping filings outside it = silent-wrong-anti-leakage-input."
- 位置：`scripts/phase_d_fetch.py:35-42, 95-103`
- 影响范围：Phase D 13D 事件流的完备性（改窗场景下的静默数据丢失）。
- 修复建议：缓存 dict 写入 start/end，`_load_cached` 校验不匹配即自失效重取。
- 修复成本：低
- 状态：已在 a8c7798f98cc40d324eed3cc638bd96f784cd3a1 修复（window-key 自失效）

### P2-1 `--limit` 冒烟模式用部分结果覆盖生产 parquet 且无标记
- 描述：`tickers = tickers[:args.limit]` 后，`phase_d_sic_map.parquet`/`phase_d_13d_events.parquet` 只含前 N 个 ticker——与全量输出同名同路径。冒烟后忘记全量重跑、直接执行 phase_d_run.py（本 commit 时点无覆盖守卫）会把 3-ticker 的退化 SIC map 提交进 confirmatory。
- 位置：`scripts/phase_d_fetch.py:71-73, 125-139`
- 影响范围：冒烟/全量工作流的安全性。
- 修复建议：--limit 时输出到 smoke 专属路径，或在 parquet 侧写 partial 标记。
- 修复成本：低
- 状态：未修复（写入路径未变；a8c7798f 在 run 侧加了覆盖守卫可拦截退化运行，属缓解而非修复）
