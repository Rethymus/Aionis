## 对照参考
FRED/ALFRED 官方文档（fred.stlouisfed.org/docs/api/fred/realtime_period.html、alfred.stlouisfed.org）与 fredapi（github.com/mortada/fredapi）：每条 ALFRED 观测含 `date / realtime_start / realtime_end` 三个日期，as-of 对齐的标准做法是 `realtime_start = realtime_end = 决策日` 取当时已发布的 vintage；默认取全部观测再按 `date` 分组取 `.last()` 得到的是**最终修订值**，嵌入未来信息。本脚本正是后者（见 P2-1）。

## 问题清单
### P2-1 宏观加载用观测日对齐 + 取最后 vintage，绕过 ALFRED as-of 纪律
- 描述：`_load_macro` 读取 `alfred_{CPIAUCSL,PAYEMS,VIXCLS}.json` 后只取 `obs["date"]`（观测期日），并 `groupby("date").last()`——ALFRED JSON 每观测期含多条 vintage 记录，文件序按 realtime 升序时 `.last()` 取的是**最晚 vintage = 完全修订值**，再以观测期日为可知日期并入 panel。代码注释自认："Use the first print (minimum realtime_start) as the knowable date / For simplicity in S0/S1, we use the observation date"。这与 `panel_alignment.build_pit_panel` docstring 声称并断言的保证 #2「宏观：vintage as-of（不使用未来修订值）」直接矛盾——调用方在上游击穿了下游断言的 PIT 不变量。CPIAUCSL/PAYEMS 均为重修订序列，属典型前视。**影响受控**：cpi/payems/vix 三列不在冻结 config #41 的 23 个特征内（13 基本面 + 10 价格），S1-M01 rank-IC 不消费这些列，故未达 P1；但产物 parquet 携带「看似 PIT、实为修订值」的宏观列，是后续任何复用者的泄漏陷阱。
- 位置：`scripts/track_b_materialize_panel.py:116-133`
- 影响范围：`data/cache/track_b_panel.parquet` 的 cpi/payems/vix 列；任何未来把这些列当特征的使用方。
- 修复建议：按 `realtime_start <= as_of < realtime_end` 选 vintage 行，可知日期用 `realtime_start`；或在本轮直接不并入宏观列以免误用。
- 修复成本：中
- 状态：未修复（main 上该函数仍为观测日 + `.last()` 实现）
