## 对照参考
- pandas 官方 `drop_duplicates` 文档（pandas.pydata.org）：不带 `subset` 即全行去重 —— 本 commit 的全行去重对「不可变 EDGAR 数据 + accession 级多交易」是正确选择（accession-only 去重会丢 86% 数据，commit message 有真实验证）。
- Airbyte "Incremental Append + Deduped" 模式（docs.airbyte.com）：业界标准是 append 原始数据后按 key 去重 keep=latest；此处因数据不可变（Form 4/A 是新 accession，从不原地改写）采用全行去重，是对不可变源的合理特例，但若上游字段表示形式变化（float 格式）会累积重复行——低风险。

## 问题清单
### P2-1 移除 per-issuer checkpoint 后，超时运行零持久化，重新制造「冷拉取死循环」
- 描述：旧版 main() 在每个 issuer 完成后即写盘 checkpoint（被本 commit 删除的 `out.to_parquet(OUT)` per-issuer 块）；新版改为所有 issuer 完成后单次写盘（`merged.to_parquet(OUT)`）。由于 `data/cache` 只在 job 成功结束时由 actions/cache 保存，中途超时的运行**一行都不落盘**——这正是本 commit 想修复的「cancelled run → 无缓存 → 再冷拉取」循环。commit 05ab7b16 的 message 亦自认："the prior single-end-save lost everything on timeout"。
- 位置：`scripts/form4_fetch.py:128-160`（该 commit 版本 main() 尾部）
- 影响范围：CI daily refresh 的 Form 4 步骤；超时即丢全部进度
- 修复建议：per-issuer write-through（每完成一个 issuer 立即 accumulate+写盘），配合 step 级 timeout 使 job 继续、缓存得以保存
- 修复成本：低
- 状态：已在 05ab7b1697 修复

### P3-1 模块 docstring 与实际去重语义不符
- 描述：docstring 写 "append/merge into the aggregate (deduplicated **by accession**)"，但实现是**全行**去重（`drop_duplicates(keep="last")` 无 subset）。恰恰是 accession-only 去重被本 commit 判定为 86% 数据丢失的 bug，文档却仍这样描述，会误导后来者。
- 位置：`scripts/form4_fetch.py:14`（该 commit 版本模块 docstring）
- 影响范围：仅文档；后来者照 docstring「优化」回 subset=["accession"] 会复现数据丢失
- 修复建议：改为 "deduplicated by exact row (multi-transaction accessions preserved)"
- 修复成本：低
- 状态：未修复（HEAD 仍为此表述，05ab7b16 未改 docstring）

### P3-2 EFTS 缓存按 (issuer, start, end) 命名，增量运行每日新增缓存文件且从不清理
- 描述：`_efts_cache_path` 为 `efts_form4_{cik}_{start}_{end}.json`；增量运行 cursor 每变一天 start 就变，每天每 issuer 新增一个 EFTS JSON，旧文件永不清理。量级小（约 5 文件/天，几 KB each），但 `data/cache` 经 GitHub cache（10GB LRU）持久化，长期有轻微膨胀与冷 miss 风险。
- 位置：`src/aionis/ingest/form4_efts.py:60-61`（本 commit 依赖的既有机制，增量语义放大了其影响）
- 影响范围：CI 缓存大小 / 恢复速度；无正确性影响
- 修复建议：EFTS 缓存键固定为全窗口（START..END），或定期清理游标窗口外的 EFTS JSON
- 修复成本：低
- 状态：待人工复核
