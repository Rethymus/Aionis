## 对照参考
fail-closed 预检模式对照 pandera 官方实践（pandera.readthedocs.io：dtype/边界校验让管线尽早失败；`lazy=True` 一次收集全部失败）。本实现为首个失败即返回，排障需多轮重跑；另 `strict=True` 式列契约（text 非空、非 None）未被覆盖——与 pandera 强调的 schema 严格性相比存在缺口。

## 问题清单
### P1-1 runner 默认把 provider_cutoff 伪造成 predict_ts —— 恰是 AUD-06 要拦的缺陷
- 描述：`forward_commit_runner.py`：`actual_provider_cutoff = provider_cutoff if provider_cutoff is not None else predict_ts`。调用方开启 `enforce_live_readiness=True` 却忘记传 `provider_cutoff` 时，门收到的正是被审计标记的「faked to predict timestamp」值；而 `_check_provider_cutoff` 对该值不做任何比对（见 P2-1），门照常 PASS。与 fail-closed 设计原则直接矛盾——未提供真实 cutoff 应当失败而非静默兜底。commit message 自己写明「Use real provider_cutoff (owner-provided), not faked to predict_ts」，代码却保留了伪造兜底。
- 位置：`src/aionis/eval/forward_commit_runner.py:279`（新增行）
- 影响范围：E3 live 路径（Slice 6/7）——LLM 知识截止未被真实校验，可能高估模型对冻结期事件的「未知性」，削弱 E3 cutoff-controlled 设计的因果论证。
- 修复建议：`enforce_live_readiness=True` 且 `provider_cutoff is None` 时直接返回 readiness_failed（新 reason code），删除 predict_ts 兜底。
- 修复成本：低
- 状态：未修复（main 上 279 行兜底仍在）

### P2-1 `provider_cutoff_faked` 是死代码——门的旗舰检查未实现
- 描述：ReasonCode 声明了 `"provider_cutoff_faked"`，但 `_check_provider_cutoff` 全函数无任何路径 raise 它：`if provider_cutoff == "unknown": ... elif ...: pass`。模块 docstring 声称「provider cutoff not faked to predict timestamp」是已实现检查（commit message 同），实际从未比对 cutoff 与 predict_ts。
- 位置：`src/aionis/eval/forward_live_readiness.py:221-235`
- 影响范围：任何调用方——伪造 cutoff 无法被门发现，审计缺陷只关闭了一半。
- 修复建议：在 `_check_provider_cutoff` 增加 `provider_cutoff == requested_predict_ts → raise ValueError("provider_cutoff_faked")`（需把 predict_ts 传入），并补测试。
- 修复成本：低
- 状态：未修复（main 上仍仅存在于 Literal 声明）

### P2-2 LLM 事件文本检查漏 None/NaN 与「空事件集」两种规避路径
- 描述：`_check_llm_event_text`：(a) `events_df.empty → return`（视为可接受），但 runner 对 e13 混合臂硬编码 `requires_llm_channel=True`，事件集为空同样意味着 LLM 边被跳过，却直接放行；(b) `events_df["text"].eq("").all()` 只捕获「全部为空字符串」，text 为 None/NaN 时 `eq("")` 为 False，部分行为空时 `.all()` 为 False——两种情况均静默通过。AUD-06 缺陷「events text zeroed」只堵住了全空串这一种形态。
- 位置：`src/aionis/eval/forward_live_readiness.py:284-297`
- 影响范围：E3 hybrid 臂——LLM 通道实质未跑却被判定 ready。
- 修复建议：改为 `if requires_llm_channel and events_df.empty: fail`；文本检查用 `events_df["text"].fillna("").str.strip().eq("").any()`（任一行为空即失败，或至少记录覆盖率）。
- 修复成本：低
- 状态：未修复

### P3-1 非 ValueError 异常绕过 fail-closed 契约
- 描述：`check_forward_readiness` 的 `except ValueError` 将 reason 归一为 `unknown_error`；但缺列（KeyError）、类型错（TypeError）等运行时异常不在捕获内，直接向上抛出而非返回 `ReadinessCheckResult(is_ready=False, reason_code="unknown_error")`——调用方拿不到统一的失败返回形状。
- 位置：`src/aionis/eval/forward_live_readiness.py:434-439`
- 影响范围：输入 schema 漂移时的调用方（runner 尚能靠异常停止，但契约形状被破坏）。
- 修复建议：`except Exception` 归一到 unknown_error（保留 structlog error + 原异常上下文）。
- 修复成本：低
- 状态：未修复
