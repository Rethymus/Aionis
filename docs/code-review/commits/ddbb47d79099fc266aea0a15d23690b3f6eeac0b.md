## 对照参考
FRED 官方 `/fred/series/observations` 文档（fred.stlouisfed.org/docs/api/fred/series_observations.html）定义 `realtime_start/realtime_end`（vintage 窗口）与 `limit/offset` 分页；fredr（sboysel.github.io/fredr）与 fredapi 的成熟做法是「以服务端文档化的 limit 页大小翻页直至短页」。本 commit 请求 `limit=100000`（远超部分文档所述 1000 上限）并靠短页终止——本次真实运行实测 FRED 返回了单页 ~2.4 万行（12 年合计 293,510 条），行为可用但依赖未文档化的服务端宽容（见 P2-1）。

## 问题清单
### P2-1 分页终止条件依赖服务端尊重超大 limit，存在静默截断风险
- 描述：`_download_dff_vintage_year` 的循环以 `if len(rows) < _DFF_PAGE_LIMIT: break` 终止，`_DFF_PAGE_LIMIT = 100_000`。若 FRED 将单次返回行数服务端钳制到请求 limit 之下（文档化上限在部分端点为 1000），首页返回 `min(钳制值, ...)` 行即小于 100000 → 循环立刻退出 → 每年只取到第一页，**无任何告警地截断** vintage 集合，缓存随后把截断快照冻结为「真相」。本次真实运行（293,510 条 ≈ 24.5k/年）证明当前服务端行为可用，但该前提未写入任何断言。
- 位置：`src/aionis/ingest/macro_dff.py:55-70`（该 commit 版本）
- 影响范围：未来 cache-miss 重取（缓存被删/新环境）时 ΔDFF vintage 不完整 → `beta_dff` 特征错误且无告警；已冻结缓存（sha256 已入 config）的 H6 重跑不受影响。
- 修复建议：以 FRED 文档化页大小（如 1000）请求并翻页至短页；或抓取后按「期望 vintage 数 ≈ realtime 窗口日数×序列日频」做下界断言。
- 修复成本：低
- 状态：未修复
