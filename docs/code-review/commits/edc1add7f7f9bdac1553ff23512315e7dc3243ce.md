## 对照参考
FRED 官方 `fred/series/observations` 文档：`limit` 上限 100000、`offset` 分页，本实现的分页参数与官方一致（fred.stlouisfed.org）。按 realtime 窗口分片规避 vintage 结果上限是社区已知模式——`fredapi`（mortada/fredapi）Issue #28 "Vintage Dates Limit" 记录了长 realtime 窗口请求超限需手动分片的问题，本 commit 的 per-year slice 正是该对策的等价实现（github.com/mortada/fredapi、pypi.org/project/fredapi）。

## 问题清单
### P2-1 realtime 窗口年份硬编码 + 缓存短路 → 跨年后静默陈旧
- 描述：`_REALTIME_END_YEAR = 2026  # current year` 与 `_REALTIME_START_YEAR = 2015` 为模块常量；`_fetch_daily_vintages_per_year` 在 `cache_file.exists()` 时直接返回旧缓存且永不重取。2027 年起循环仍止于 2026（新 vintages 不再获取），且旧 `alfred_GS10.json` 命中短路掩盖缺年——`_daily_asof_series` 对超出窗口的 as_of_dates 静默产出 NaN，无任何断言/告警。下游 z-score → 缺失 → 覆盖率下降只体现在 log 计数里。该缺陷自 `macro_dff._DFF_REALTIME_END_YEAR` 原样继承（两处需同步修）。
- 位置：`src/aionis/features/macro_headline.py:59-60`（及 `:121` 的 range 循环）
- 影响范围：`fetch_us_macro_4` → A3 broadcast join → asymmetric41 confirmatory 管线的 US macro 4 特征；跨年后特征静默失效
- 修复建议：`_REALTIME_END_YEAR` 改为 `datetime.now().year` 动态推导，并在 as-of 合并后断言"as_of_dates 最大日期 ≤ 缓存最后 realtime_start"否则 raise/warn；或在 `_fetch_daily_vintages_per_year` 缓存命中时校验末年覆盖
- 修复成本：低
- 状态：未修复（main 上仍是 2026 硬编码；macro_dff 同款未修）
