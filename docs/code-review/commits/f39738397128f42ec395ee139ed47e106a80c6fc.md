## 对照参考
内容寻址 provenance 的成熟范式是 in-toto/SLSA attestation（in-toto.io、slsa.dev）：statement 中 subject 用 digestSet 绑定内容哈希，且验证方独立重算摘要比对——即「哈希必须可被验证」，本实现的 capsule_id 缺少对应对端（见 P2-1）。确定性序列化方面，RFC 8785 JCS 是标准 JSON 规范化方案；本实现用 `json.dumps(sort_keys=True, separators=(",",":"))` 是其简化近似，对本 schema（无浮点歧义字段，temperature 由字符串承载）足够，但对含 float 的扩展字段需注意非 JCS 差异。出处域名：slsa.dev、in-toto.io、datatracker.ietf.org（RFC 8785）。

## 问题清单
### P2-1 capsule_id 无完整性校验：加载与创建均信任调用方给的值，篡改不可检测
- 描述：`compute_capsule_id` 仅在 `capsule_id is None` 时计算内容哈希：
  ```python
  if self.capsule_id is None:
      ...
      object.__setattr__(self, "capsule_id", capsule_id)
  ```
  两个缺口：(a) 构造时显式传入的 `capsule_id="a"*64` 通过 pattern 校验后原样保留，从不与内容重算比对；(b) `load()/from_json` 读入带 capsule_id 的文件时同样跳过重算——文件中任何 provenance 哈希被篡改后，stale capsule_id 依旧加载成功，无任何告警。capsule 的全部价值在「provenance 可审计」，缺 verify 步骤使内容哈希沦为装饰。测试套件也只测了「自动计算」与「输入变 → id 变」，没有篡改检测用例。
- 位置：`src/aionis/reporting/reproducibility.py:292-305`
- 影响范围：所有依赖 capsule 做复现审计的下游（RD 系列任务、人工复核）；篡改/意外损坏均不可见。
- 修复建议：增加 `verify() -> bool`（重算 canonical 哈希与 capsule_id 比对）并在 `load()` 后默认调用或提供 `load(path, verify=True)`；创建路径对显式传入的 capsule_id 也做重算断言。
- 修复成本：低
- 状态：未修复（该文件后续无 commit）

### P3-1 `object.__setattr__` 绕过 pydantic 赋值机制
- 描述：model_validator 内用 `object.__setattr__(self, "capsule_id", capsule_id)` 原因是「immutable pattern」注释，但 model_config 未设 `frozen=True`，模型本身可变；直接 `self.capsule_id = capsule_id` 即可（也未设 validate_assignment，无额外开销）。绕过 pydantic 的 setattr 通道是坏味道，未来若开启 validate_assignment 此处会静默失去校验。
- 位置：`src/aionis/reporting/reproducibility.py:305`
- 影响范围：维护性；无当前行为缺陷。
- 修复建议：改普通赋值，或将 capsule_id 完全移出模型、由独立工厂函数计算后传入。
- 修复成本：低
- 状态：未修复

### P3-2 ProviderKind 与 extraction/providers.py 手工双写

- 位置：`src/aionis/reporting/reproducibility.py:45-59`

- 修复成本：低
