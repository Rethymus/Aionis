## 对照参考
`key: <prefix>-${{ github.run_id }}` + `restore-keys: <prefix>-` 正是 actions/cache 官方 README「Update a cache」一节给出的不可变缓存滚动更新模式（缓存不可变 → 每次运行存新条目、恢复时前缀匹配最近一条）；GitHub 自家 gh-aw 工具也把该组合列为合法的 "last one wins" 模式。官方文档同时提示该模式会较快消耗存储配额（约 10GB，超出后 LRU 淘汰）。出处：github.com/actions/cache（README/tips-and-workarounds）。

## 问题清单
### P3-1 run_id 键模式每日新增全量缓存条目，存储配额 churn
- 描述：`key: data-cache-${{ github.run_id }}` 意味着每个 daily run 在 post 阶段保存一份**全新**的 `data/cache` 全量快照（Form 4/13D/COT/macro 数年累积的 per-accession 缓存），且旧条目只有被 restore 命中才算"使用"。按日运行会快速逼近 GitHub 仓库 10GB 缓存配额，触发 LRU 淘汰时可能把 `uv-${{ runner.os }}-...` 依赖缓存一并挤出去，造成冷依赖安装回潮。
- 位置：`.github/workflows/refresh-terminal-data.yml:71-76`（该 commit 版本）
- 影响范围：CI 时长波动（uv 缓存被逐后回到慢路径）；不污染数据（data/ 本身 gitignored）。
- 修复建议：可接受现状（官方模式）；若要降 churn，可在 save 前清理过期子目录，或改用按周/按日期分桶的 key，或用 `actions/cache/save`+`restore` 拆分并控制保存频率。
- 修复成本：低
- 状态：未修复（属可接受的运维取舍，非缺陷）
